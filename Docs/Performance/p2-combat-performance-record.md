## 3. 测量结果

| 阶段 | 帧数 | GC/帧中位数 | GC/帧峰值 | 主线程中位数 | 主线程峰值 |
| --- | --- | --- | --- | --- | --- |
| 空闲基线（狼休眠） | 22,073 | 1,001 B | 615,465 B | 0.331 ms | 1.578 ms |
| 战斗稳定态 | 23,149 | 1,001 B | 615,465 B | 0.319 ms | 1.794 ms |

**战斗相对空闲基线的每帧分配增量：0 B**（预算 ≤ 512 B）。

### 为什么用增量而不是绝对值

Editor 自身有固定的每帧分配（这里是 1,001 B/帧），它跟战斗代码没关系。
两个阶段相减之后剩下的才是**战斗路径本身**的分配，而这正是
"战斗稳定态 0B GC/frame" 真正要回答的问题。

两个阶段的 GC 中位数与峰值**完全相同**（1,001 B / 615,465 B），
说明这些分配全部来自 Editor，战斗没有贡献任何每帧垃圾。
这与设计是一致的：行为树节点在构造时建好一次、决策只调用委托；
物理查询走 `NonAlloc`；`MaterialPropertyBlock` 不实例化材质；
`MonsterPresentationState` 是 `readonly struct` 且实现 `IEquatable` 以避免装箱。

## 4. 结论对照

| 指标 | 目标 | 本次 | 结论 |
| --- | --- | --- | --- |
| 战斗稳定态 GC/帧 | 0 B 新增 | **0 B（相对基线）** | **通过** |
| 主线程帧时 | ≤ 8 ms | 0.319 ms（中位数）、1.794 ms（峰值） | 仅作上限参考 |
| 渲染线程帧时 | ≤ 8 ms | **未验证** | 取不到可信值 |
| GPU 帧时 | ≤ 14 ms | **未验证** | 取不到可信值 |
| 总帧预算 | ≤ 16.67 ms | **未验证** | 取不到可信值 |

主线程那一行为什么只是参考：Editor 的开销大于播放器，所以这个数偏**悲观** ——
真机只会更快，但它不能当作"主线程 ≤ 8 ms 已验收"的证据，因为分辨率是 640×480
且没有真实渲染负载。

渲染线程、GPU 与总帧预算为什么是未验证：自动化以 `-nographics` 运行，
GPU 是 `Null Device`，这三项在这种环境下**没有可信值**。
按规范要求，这里写"未验证"而不是填一个看起来好看的数。

## 5. 仍需人工完成

1920×1080 下的渲染线程、GPU 帧时与总帧预算必须由人完成：

1. 用 Development Build 构建播放器（当前已有一份 Windows x64 构建产物在
   `artifacts/build/win64/`，`Development Build = true`）；
2. 启动它并把 Unity Profiler 连上去（**Deep Profile 保持关闭**）；
3. 进地图二，预热至少 10 秒让首次加载与 Shader 编译过去；
4. 在"巡逻 → 追击 → 普攻 → 吐息 → 受击"的循环中采至少 300 帧稳定战斗；
5. 记录主线程、渲染线程、GPU 帧时与 GC Alloc/frame。

本文件的 GC 结论不受这一步影响 —— 那一项已经测到，且与渲染无关。
