# ADR-0010：用CSV源表加本地配置编译器取代运行时表格读取

- 状态：已接受
- 日期：2026-09-08

## 背景

P1要把价格、概率、物品、英雄、武器等级、锻造配方、签到奖励、成就与账号等级奖励全部数据化。此前的任务表里出现过Luban，也出现过"Unity运行时直接读xlsx"的写法。两者都不适合当前项目：

- Unity运行时读xlsx要引入Excel互操作或一个体积可观的第三方解析库，而且客户端本来就不该成为数值的权威来源。
- 云主机是2 vCPU、2 GiB的单机，按ADR-0008它不安装任何构建工具。在云端跑配置编译是不可能的。
- 数值同时被服务端（权威判定）和客户端（展示）使用。如果两端各维护一份，迟早会不一致，而不一致的表现是玩家看到一个价格、被扣另一个价格。

## 决策

- 源表是**UTF-8带BOM的CSV**，放在`Config/Source/`，用Excel直接打开编辑。带BOM是为了让Excel正确识别中文而不是乱码。
- 一个本地.NET 10控制台程序`Tools/Config/Naraka.ConfigCompiler`把CSV编译成规范化JSON。它只在本地或CI运行，**绝不在云主机上运行**。
- 生成物写到`Shared/Generated/Config/`，并镜像到`NK/Assets/StreamingAssets/Config/`供Unity只读加载。数据模型只在`Shared/Config/NarakaConfigModels.cs`写一份，由编译器镜像到`NK/Assets/Game/Generated/Config/`，服务端则直接链接原文件。
- 模型使用public字段与PascalCase JSON，这样同一个文件既能被Unity的`JsonUtility`用，也能被`System.Text.Json`（`IncludeFields = true`）用，不需要两套模型或一层转换。
- 编译器固定编码与`CultureInfo.InvariantCulture`，并强制校验：ID唯一；外键存在；价格与数量非负；`StackLimit > 0`；概率权重合法；抽奖品质只允许白/蓝/紫/金/红；每个奖池权重和大于0；20抽保底品质必须有可兑现的奖励；武器等级连续且不重复；锻造配方引用的材料存在；签到天数在1–7；账号等级奖励等级合法；英雄/技能/武器的展示顺序确定。
- 输出按稳定ID排序，LF换行、无BOM，附`configVersion`、`schemaVersion`与SHA-256清单。**相同输入必定产生字节相同的输出。**
- 任何校验失败返回非0退出码，并指出源文件与行号。编译器**绝不输出密码、连接串或环境变量值**。
- 运行时：服务端加载并校验生成配置，**经济判定只信服务端配置**；Unity加载同一版本只读用于展示，客户端配置对价格、概率、奖励**不具权威性**。
- Bootstrap预检继续校验配置版本。CI在跑测试之前先执行`--check`：生成物与源表不一致就直接失败。
- 不为读CSV或JSON引入大型第三方依赖。CSV解析是编译器内一个约200行的RFC4180实现，JSON用.NET标准库与Unity内置的`JsonUtility`。

## 结果

- 策划改数值只需要编辑CSV并跑一次编译器；改错了会在本地立刻失败并指到行，而不是在游戏里表现为一个诡异的价格。
- 客户端与服务端不可能拿到不同版本的配置：同一份生成物、同一个哈希、CI有一致性门禁。
- Luban不再纳入本项目。若将来确实需要更复杂的表结构（多语言、继承、引用数组），再单独评估，而不是现在为可能的需求引入一整套工具链。
- 当前生成配置`ConfigVersion`为`p1-config-5e52cf730692`。它与Bootstrap登录门禁是**两个独立的版本号**；完整P1集中发布按ADR-0008把后者提升为`p1-config-1`，生成配置哈希不因此改变。
