# ADR-0008：按大类集中执行低内存云端发布

- 状态：已接受
- 日期：2026-09-07

## 背景

当前开发环境是2 vCPU、2 GiB内存的单台Windows Server 2016，Host、MySQL与SSH共同运行。P1.1客户端曾连接仍停留在P0应用消息表的云端Host；客户端进入大厅后发送新增消息，旧Host又把连接级异常升级成后台服务失败，最终导致整个进程退出。该事故不是数据库或云主机内存耗尽，而是客户端、服务端和数据库迁移未作为同一版本化发布单元。

频繁在云主机编译、安装SDK或逐个按钮部署，会增加资源压力、版本漂移和人工失误。另一方面，商店、仓库、签到、抽奖、锻造、好友、聊天和战斗等服务端权威功能仍会自然产生新的应用契约与数据库迁移，不能承诺永不更新云端。

## 决策

- 云端发布以“一个大类功能完成”为最小批次，不按单个按钮、UI微调或普通客户端修复发布。UI布局、美术、场景表现与不改变服务端契约的客户端工作不触发云端部署。
- 每个可部署版本必须来自干净Git提交，通过服务端CI和Unity EditMode/PlayMode验收。本地候选包可以显式允许脏工作区或跳过Unity，但必须标记为不可部署，云端脚本必须拒绝它。
- 编译、测试、NuGet恢复、自包含发布与压缩全部在本地或受信任CI完成。云主机不安装.NET SDK、Visual Studio、Unity、GitHub Runner、容器或其他构建工具。
- Host、自包含DatabaseMigrator、迁移SQL、Git提交、版本门禁与两个包的SHA-256共同写入发布清单。云端先校验清单和哈希，再停止唯一Host进程。
- 数据库迁移必须幂等，并采用扩展优先策略：同一发布只新增向后兼容的表、列、索引或数据，不在切换Host的同一步骤删除旧结构。这样Host启动失败时可以恢复上一版二进制；收缩或删除结构必须推迟到后续单独验收的发布。
- 云端部署顺序固定为：资源与GUI检查、停止Host、解压、迁移dry-run、首次迁移、重复迁移验证、旧目录备份、新目录原子切换、健康检查、单进程与loopback监听检查。任何Host验收失败都恢复上一版目录，失败版保留供排查，不直接删除。
- 云端稳态只运行MySQL、Host与SSH。Host守护器使用现有计划任务中的单个PowerShell父进程，异常退出后至少等待30秒再启动，低于256 MiB可用内存时延迟启动，避免并行实例与快速重启风暴。日志达到阈值才轮换，只保留有限历史。
- Bootstrap版本门禁必须代表实际应用契约。部署新增业务消息的Host时同步提升ConfigVersion或最低客户端版本。当前P1A仍报告`p0-config-1`是已知过渡状态；在下一次包含新应用契约的集中发布前必须消除，不单独为标签立即再部署。
- Unity界面布局、UXML/USS、场景挂载、美术资源与Inspector操作继续由用户负责。本决策不授权自动修改这些内容。

## 结果

- 云端仍需要随服务端权威大类功能升级，但发布频率从“小功能级”降低为“里程碑级”。
- 以后常规流程收敛为复制一个版本目录并执行一条已校验脚本；失败能够恢复旧Host，且云端不承担构建负载。
- 单机开发环境仍不构成生产级高可用。云平台、操作系统或磁盘故障无法靠进程脚本消除；正式发布前仍需独立备份、监控、TLS、密钥托管和容量方案。
- 当前P1A线上包来自过渡期工作区，已经完成70/70服务端测试、Unity EditMode 52通过/1跳过和PlayMode 3/3，并通过真实登录验收。下一次集中发布前必须把对应源代码纳入干净Git提交和正式发布清单。
