# ADR-0011：用发放记录与不可变流水实现初始货币，而不是改动已部署迁移

- 状态：已接受
- 日期：2026-09-08

## 背景

新的玩法基线要求新账号拥有铜币、幻丝、金币各1000（见ADR-0009）。已经部署到云端的迁移`0001`与`0002`把三种余额初始化为0，而这两个迁移**不允许修改**——它们已经在云端执行过，改动文件既不会重新执行，也会让本地与云端的迁移哈希对不上。

直觉方案有两个，两个都不能用：

- 把列的`DEFAULT`改成1000：这需要`ALTER TABLE`已部署的表，而且默认值只影响新插入的行，对既有账号无效。更根本的问题是，**列默认值不是资产的来源**——它没有留下任何"谁在什么时候发了多少"的记录。
- 写一句`UPDATE account_progression SET copper = 1000 WHERE copper = 0`：这会把一个正好花光铜币的老玩家的余额凭空补满，而且重复执行会重复发放。

## 决策

- 新增两张表，不动任何已部署结构：
  - `account_grants(account_id, grant_key)`：一次性发放的记录，主键就是幂等键。
  - `currency_ledger`：不可变的货币流水，唯一键`(account_id, currency_id, reason, reference_id)`。
- 账号首次登录时，`EnsureProvisionedAsync`在**一个事务**里完成：写入`account_grants`的StarterGrant行、按配置累加三种余额、为每一笔发放写入`currency_ledger`。
- 发放是**累加**而不是覆盖。规则是"这个账号有没有领过StarterGrant"，不是"这个账号的余额是不是0"。因此：
  - 老账号第一次登录会拿到1000，不管它当前余额是多少；
  - 花光了的账号不会被补满；
  - 重复登录不会重复发放，因为主键会拒绝第二次插入。
- 发放金额来自配置的`currencies`表（`StarterGrant`列），不写死在代码里。
- 每一笔初始发放都进入不可变流水。任何时候都可以回答"这1000铜币是哪来的"。

## 结果

- 已部署的`0001`与`0002`保持字节不变，有测试锁定它们的哈希。
- 初始货币的语义从"列的默认值"变成"一笔有记录、可审计、幂等的发放"，与后续所有货币变动（购买、锻造、抽奖、签到、奖励）走同一套流水。
- 本轮**未对云端NK库执行迁移**。`0003`–`0009`只在本地dry-run验证过语句数与语法。
- 代价是每个账号首次登录多一次事务。这个成本是一次性的，换来的是不需要在迁移里写任何猜测性的数据修补。
