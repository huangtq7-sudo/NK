# ADR-0023：任务与对话的服务端权威边界

- 状态：已接受（用户 2026-10-11 批准 P4.1 实施）
- 日期：2026-10-11
- 对应阶段：P4.1

## 背景

P4 需要两名 Idle NPC、范围内按 E 的底部逐字对话和一条可领取奖励的主线。账号经验只能来自任务，任务奖励直接写入账号且死亡不清空；服务端必须防止换 RequestId 重复领奖，同时不能把“客户端点了继续”当成任意领奖的证明。服务端当前不知道玩家位置和所在地图，战斗事实也尚未有可信生产链（见 ADR-0024）。

## 决策

1. 任务状态链固定为 `Locked → Available → Accepted → InProgress → ReadyToSubmit → RewardPending → Claimed`。Locked/Available 由服务端推导，不落库；落库实例单向前进。规则集中在纯领域的账号级聚合 `QuestLog`，存储层只在一个事务、一把账号锁里重建它并落地应用层给出的决定。
2. 新增应用消息 `MsgQuestRequest=67`/`MsgQuestResponse=68` 与能力 `quest`，按 ADR-0007 只追加，不改冻结传输。请求只携带意图（任务、目标、读完的对话），没有账号、奖励、数量或经验字段。
3. 对话目标的证据是“客户端声称读完对话 + 服务端核对目标顺序、对话归属、活动远征、服务端时间最短时长与请求频率”。它不证明玩家站在 NPC 旁边，因此只用于低价值、一次性、不可刷的对话目标。配置编译器只允许启用已实现服务端校验路径的目标类型（当前只有 `Talk`）。
4. 领取在一个事务内完成：`account_reward_claims(Quest, 实例键)` 主键防止换 RequestId 重复领取；物品、货币与 `currency_ledger(QuestReward)`、`account_xp` 与新表 `account_xp_ledger`、`account_progression.account_level`、`idempotency_records` 同时提交，任一步失败全部回滚。背包放不下时整体拒绝、保持待领取，不溢出到邮件。
5. 客户端只显示服务端日志：不本地推进、完成或发奖。对话 Model/Controller 与任务无关，只通过“读完/取消”回调交给任务交互控制器；Collider 只在 View 中产生候选。对话期间通过 `IGameplayInputLock` 锁角色输入，不暂停世界。
6. 主线对话目标类别为 `Dialogue`，不产生成就来源事件，不计入大厅战斗任务。

## 实施记录（2026-10-12）

本机真实MySQL冒烟发现：在不存在的幂等行上做加锁读会产生间隙锁，两条不同RequestId的并发领取随后插入同一间隙即死锁。已改为先锁账号货币行与资料行（与远征结算同序），再在锁内普通读幂等记录，并对死锁/锁等待超时整体重试一次；修复后真实库并发领取恰好一次成功。

## 结果

- 首条主线可以在本机 Host 上完成接取→对话→提交→手动领取→重登恢复，经验与奖励各只发放一次。
- P3 云端不声明 `quest`，P4 客户端连接它时不发送 67，只能播放日常对白。
- 新增迁移 `0011_p4_quests.sql`（3 张表），已部署迁移不变。
- 代价：对话目标的可信度有限，已在本 ADR 和代码注释中如实记录；战斗类目标必须等 ADR-0024 批准并实现后才能启用。
